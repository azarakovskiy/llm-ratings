# AA role metric bases: indexes, cost and latency

Researched **2026-10-28** for ticket 32, *Verify AA index cost bases and latency semantics*. This is a factual prerequisite, not a choice of role mappings, objectives, floors or timing policy. Timing is explanatory only under the parent's confirmed HITL decision. No product code, glossary or tracker was changed.

## Decision-safe answer

- **Matched index/task-cost value is available for Intelligence only:** `data[].evaluations.artificial_analysis_intelligence_index` and `data[].artificial_analysis_intelligence_index_cost.cost_per_task.total_cost`. Their quotient is Intelligence points per USD of an **Intelligence Index task**, not expected production-task ROI. A missing or zero denominator does not supply a valid finite value ratio. [S1, S2, S4]
- **No Coding-index or Agentic-index per-task cost was established.** Neither the current Free nor paid language-model schema publishes an `artificial_analysis_coding_index_cost` or `artificial_analysis_agentic_index_cost`, or an equivalent area-index task-cost field. The published methodology defines the available task cost against the full Intelligence workload. Reusing it would produce Coding/Agentic points divided by **Intelligence-workload** cost, not same-index cost efficiency. This is a possible explicitly chosen cross-workload proxy, not a measured Coding/Agentic value result. The same qualification applies to a cheapest-above-floor rule or frontier using that cost axis. [S1–S4; inference from the different named workloads]
- **The API Coding score is not the Coding Agent Index.** Coding has documented scientific code-generation and terminal-agent components; it is not an ordinary-code-only score, nor a dedicated repository-SWE-only score. The exact current complete component list and weights of the API's Coding and Agentic fields could not be verified after the v5 change. Current public sources contain an unresolved legacy/current mismatch; details below. Do not replace either API field with the v5 category of the same general name. [S1, S3, S6–S9]
- **Four explanatory performance displays have Free-schema fields**, when non-null: TTFT, time to first **answer** token, output tokens/s, and end-to-end time for **500 answer tokens**. TTFT can stop at the first reasoning token; first-answer time includes thinking; output speed is generation throughput after generation starts; end-to-end is a standardized synthetic response estimate, not coding-task wall time. The Free route does not document its selected prompt preset or its exact cross-provider aggregation algorithm. [S1, S2, S5, S10]

## 2. What each index means, and what is unresolved

### Intelligence: current v5.0 is explicit

AA describes the Intelligence Index as a synthesis of language-model capability, primarily **text-based and English-language**. It does not claim direct applicability to every use case; image, speech and multilingual benchmarking are separate. Current v5.0 has nine evaluations, with four equally weighted categories: [S3, S6]

| Category | Share | Evaluations and share of the whole Intelligence Index |
|---|---:|---|
| Knowledge Work | 25% | AA-Briefcase v1.1 15%; AutomationBench-AA 5%; GDP.pdf 5% |
| Coding | 25% | FrontierCode 2.0 15%; Terminal-Bench 4.0 10% |
| Science | 25% | Terminal-Bench-Science 0.1 15%; CritPt v2 hard subset 10% |
| General | 25% | AA-Omniscience v1.1 15% (accuracy 10%, non-hallucination 5%); HLE-Diamond 10% |

The v5 Coding **category** is agentic: real open-source repository changes (FrontierCode 2.0) and terminal-based task execution (Terminal-Bench 4.0). This does **not** establish that `artificial_analysis_coding_index` has been changed to that category. [S3, S6]

`intelligence_index_version` at the response root is authoritative for the scores in a response. The current documentation says v5.0, but the schema's illustrative response still says 4.1. An example is not evidence that the live endpoint is still on 4.1. Major changes alter interpretation; minor and patch changes can change evaluations, graders, normalization, weights or scores. The response reports major.minor only, not patch. [S1 `info.description`, `components.schemas.IntelligenceIndexVersion`; S2 “Intelligence Index versioning”]

### Coding and Agentic: API identities are clear; current full formulas are not

Current tiered docs say, verbatim, that `artificial_analysis_coding_index` and `artificial_analysis_agentic_index` “are derived from subsets of the Intelligence Index evaluations and are not separately versioned.” Their schemas describe them only as composite scores. They do not enumerate current components or weights. [S1 `info.description`, `components.schemas.FreeEvaluations`; S2 “Intelligence Index versioning”]

### Do not substitute the separate Coding Agent Index

The **Coding Agent Index v2.0** is an equal-weight mean of **FrontierCode v1.1, Terminal-Bench 4.0 and SWE-Atlas-QnA-AA**, covering 290 tasks, three attempts per task. Its rows are **agent variants**, with execution/reasoning settings, not just language-model rows. It covers implementation, terminal workflows and repository Q&A. This differs from both the API Coding composite and II v5's Coding category. [S9]

This separate benchmark **does publish cost per task and agent wall time on its website**. Cost is a pooled per-task-attempt pay-per-token API average across its suite, including cache distinctions where available; missing telemetry is excluded rather than zeroed. It is not consumer subscription price or full deployment cost. No mapping of those numbers onto `data[].evaluations.artificial_analysis_coding_index`, and no corresponding route/field in the published language-model API schema, was found. Therefore this is **not** evidence that the project's Free Coding score has a matching cost. [S1 `paths`, `components.schemas.ModelDataExternal`; S9 “Efficiency Metrics”, “Agent Settings”; S11 “Cost”]

## 3. Cost: measured workload, list price and blended price are different

### The available task-cost basis

AA currently defines **Cost per Task** as the weighted-average USD cost to complete **one Intelligence Index task**. Each evaluation's input, cache-hit, cache-write, reasoning and answer-token costs are divided by task count and weighted by its Intelligence Index weight. Prices are first-party API rates or the median across providers. Longer answers and more reasoning tokens can therefore increase task cost even when list token prices are identical. Use the published per-task field, not whole-suite `total_cost` divided by an invented common task count. [S3 “General Testing Parameters”; S4 “Definitions”; S6 “Cost per Intelligence Index Task”]

This is **benchmark token consumption repriced with current pricing and representative caching**, not necessarily a historical invoice paid at evaluation time: AA uses provider-reported evaluation token counts where available (canonical-tokenizer fallback otherwise), and combines them with live measurements of typical cache-hit rate rather than the cache result of the one evaluation run. Current performance docs say cache rates are measured about every 18 hours and updated monthly from the median of the previous four weeks. The metric is not a prediction of a user's role-specific task expenditure. [S3 “General Testing Parameters”; S4 “Definitions”; S5 “Testing Frequency”, “Token Measurement”]

| Cost/price item | Exact response path, relative to `data[]` | Free access and meaning |
|---|---|---|
| Intelligence suite total | `artificial_analysis_intelligence_index_cost.total_cost` | USD for the whole II evaluation, not USD/task. Outer cost object may be null. |
| Intelligence task cost | `artificial_analysis_intelligence_index_cost.cost_per_task.total_cost` | Weighted USD/II task, rounded to 4 decimals. `cost_per_task` may be null when token or price data is incomplete. |
| Uncached input list price | `pricing.price_1m_input_tokens` | USD per 1M input tokens; nullable. |
| Output list price | `pricing.price_1m_output_tokens` | USD per 1M output tokens; nullable. Do not treat it as USD/task. |
| Cache read/write list prices | `pricing.price_1m_cache_hit_tokens`, `pricing.price_1m_cache_write_tokens` | Both are present in `FreePricing`, despite the overview's shorter “input/output prices” description. Nullable when cache pricing is not reported. |
| Coding/Agentic task cost | **No published path found** | Neither Free nor `ModelDataExternal` has an area-index cost object. |
| Blended token prices | `pricing.price_1m_blended_3_to_1`, `pricing.price_1m_blended_7_to_2_to_1` | Paid schema, not `FreePricing`. Respectively assume 3:1 input:output and 7:2:1 cache:input:output. These are declared token mixes, **not observed task costs**. |

Source for every field in this table: [S1 `components.schemas.FreeModelData`, `FreeIntelligenceIndexCost`, `FreeIntelligenceIndexCostPerTask`, `FreePricing`, `ModelDataExternal`, `Pricing`, `IntelligenceIndexCost`, `IntelligenceIndexCostPerTask`]. General definitions of list/native-token pricing and the 7:2:1 blend: [S4 “Definitions”].

Pro adds II input/reasoning/answer cost breakdowns, aggregate II token counts, and detail-only `data.evaluation_token_counts.<evaluation>.{input_tokens,answer_tokens,output_tokens,reasoning_tokens}`. These additions still do not publish a Coding/Agentic task-cost denominator or settle the current area-index weights. Free lacks the per-benchmark usage needed to reconstruct one. No task mix, cache rate, token use, repeat convention or area weighting was invented here. [S1 `components.schemas.ModelDataExternal`, `EvaluationTokenCounts`, `EvalTokenCounts`, `IntelligenceIndexCost`]

**What calculations are supported:** Intelligence score / II task cost is a transparent project-defined quotient on a matched benchmark basis. AA does not publish that quotient as an expected-success-per-dollar measure; composite index points are not a probability or a ratio-scale measure of useful work. Coding/Agentic score / II task cost is arithmetically possible but carries a mismatched-workload denominator. List or blended-token prices cannot turn it into same-index task value without an explicit workload model. This report does not choose any such proxy or change the existing glossary. [S3–S4; inference about units and scope]

## 4. Timing and throughput: supported displays and their limits

All four Free fields are in `components.schemas.FreeModelPerformance`, under `data[].performance`. They are nullable numbers. The table gives factual display labels, not a recommendation or a selection/tie-break rule. [S1, S2]

| Field suffix after `data[].performance.` | Accurate explanatory label | Definition and reasoning treatment |
|---|---|---|
| `median_time_to_first_token_seconds` | Median TTFT, seconds | Request sent → first response token. If reasoning tokens are returned, that first token can be reasoning, **not an answer**. [S4, S5 “Key Definitions”] |
| `median_time_to_first_answer_token_seconds` | Median time to first answer token, seconds, including thinking | Request sent → first answer token after any thinking. The website says that for non-streaming models this is time to receive the completion. It need not equal TTFT. [S5 “Key Definitions”; S10 “Latency”] |
| `median_output_tokens_per_second` | Median output generation speed, tokens/s | Tokens received per second after the first token/chunk. Performance token counts use `o200k_base`, not each model's billing tokenizer. For reasoning models that do not expose all reasoning tokens, AA uses the **last 80% of answer chunks** for output speed. This is neither answer-start delay nor full-task duration. [S4; S5 “Token Measurement”, “Output Speed Calculation”; S10 “Speed”] |
| `median_end_to_end_response_time_seconds` | Median estimated response time for **500 answer tokens**, seconds, including thinking | API convention fixes 500 answer tokens unless the field says otherwise. The website describes a synthetic estimate combining first-token/input time, thinking and generation of 500 answer tokens. It is not a measured completion time for the whole Intelligence/Coding/Agentic workload. [S1 `info.description`; S2 “Data conventions”; S10 “End-to-End Response Time”] |

### Workloads and measurement windows

Current performance methodology specifies: [S5 “Workload Types”, “Load Scenarios”, “Testing Frequency”, “Prompt Generation”, “Measurement Representation”]

- **1k input:** about 1,000 input tokens and at least 1,000 answer tokens.
- **10k input:** about 10,000 input tokens and at least 1,500 answer tokens; default on the **website** since 2026-03-02.
- **100k input:** about 100,000 input tokens and at least 2,000 answer tokens.
- **Vision:** one 1-megapixel image, about 1,000 input and 1,000 output tokens.
- Single-request load versus **10 simultaneous requests**. Standard 1k/10k/vision workloads run about every three hours; the parallel 1k workload runs daily; 100k runs weekly.
- New prompts are generated for each run and shared across covered endpoints. Tasks include explanation/summarization, question/answer generation, comparison, translation and visual artifact generation. Prompt type affects speed, including through speculative decoding.
- Displayed performance is median/P50 over **72 hours**, except the weekly 100k workload, which uses **14 days**. This is not a per-task p95 or an uptime/reliability guarantee.

For the paid endpoints that accept `prompt_type`, the current schema enumerates `medium` (1k, one request), `long` (10k, one; default), `100k`, `vision_single_image`, and `medium_parallel` (1k, ten). **There is no current `coding` preset in that enum.** The Free route declares only `page`: it does not declare `prompt_type`, report a chosen prompt preset in its response envelope, or document a Free-specific default. Therefore **“Free medians are 10k/single” remains an unsupported assumption**, even though paid defaults and the website default are 10k. The fixture does not resolve this. [S1 `paths./api/v2/language/models/free.get.parameters`, `components.parameters.prompt_type`, `components.schemas.LLMModelsFreeResponse`; S2 reference]

### Reasoning and end-to-end estimates

AA bases “average reasoning tokens” on **60 diverse prompts** covering personal/commercial queries, coding, math, science and other topics, including prompts from MMLU-Pro, AIME 2025 and LiveCodeBench. Where the average is unavailable or not yet calculated, AA assumes **2,000 reasoning tokens**. This is a separate performance-estimation workload, **not** the token usage of each current index's benchmark tasks. The Free schema does not expose the per-row reasoning-token estimate or a measured-versus-default flag. Do not describe every end-to-end value as a fully observed task runtime. [S4 “Average Reasoning Tokens”; S5 “Key Definitions”; S1 `FreeModelPerformance`]

The website also publishes **Time per Intelligence Index Task**. It is derived from benchmark answer/reasoning token use divided by native-token answer speed on the 10k workload, weighted by II weights, and **excludes TTFT and overhead**. It is not the Free `median_end_to_end_response_time_seconds`, nor a whole-agent wall clock. No Time-per-Task field appears in `FreeModelData`. The separate Coding Agent Index's measured agent wall time is another distinct basis. [S4 “Time per Task”; S6 “Speed”; S9; S10 “Time per Intelligence Index Task”; S1]

### Comparison limits that must stay visible

1. **Endpoint/aggregation ambiguity:** the API schema calls model performance “across all providers serving this model.” Website tooltips say first-party API, otherwise median across providers. These descriptions are not identical; the public sources do not settle the Free endpoint's selection/pooling algorithm. Do not promise that a Free model median describes one chosen hosting provider, or the same endpoint used for a cost estimate. Per-provider data and time series require Commercial access. [S1 `FreeModelData.performance`, `FreeModelPerformance`, `ModelPerformance`; S2 “Tiers”; S10]
2. **Network and workload:** TTFT includes network latency. AA tests mainly from Google Cloud `us-central1-a`; this can favor or disadvantage provider locations. Longer prompts can increase TTFT and lower output speed; output type can also change speed. Figures are customer-observed API performance, not maximum hardware throughput. [S4 “Scope”; S5 “Workload Types”, “Technical Details”, “Known Limitations”]
3. **Effort/configuration:** first-party v5 results explicitly distinguish low/max effort and show changes in both score and task cost. The API schema has separate row identity (`id`, `name`, `slug`), but **no structured `reasoning_effort` field**; even `reasoning_model` is paid-only. The fixture has separate effort rows, and local parsing derives effort from names. Do not combine one variant's score with another's cost/timing or assume identical low/high/max labels imply equal budgets across labs. The last point is an unsupported equivalence, not an AA guarantee. [S1 `FreeModelData`, `ModelDataExternal`; S6 “Effort settings matter”; L2, L5]
4. **Missingness:** null means not measured or not applicable, never zero. The cost object can be null; `cost_per_task` can be null for incomplete token/pricing data; each performance field can independently be null. A paid-only omission is an access restriction, not evidence of zero. Current area-score schemas allow null but do not specify each area's full completeness rule. [S1 `FreeEvaluations`, `FreeIntelligenceIndexCost`, `FreeModelPerformance`, `ModelDataExternal`; S2 “Data conventions”]
5. **Different token units and aggregates:** evaluation-cost tokens use native/provider usage; performance tokens use a standardized tokenizer, with the native-token exception stated for Time per Task. These units cannot be silently interchanged. Also, a median of synthetic response durations is not guaranteed to equal a formula applied to separately aggregated median TTFT and throughput. Do not recompute a missing published metric as an equivalent measured one. [S3–S5; inference about non-commuting aggregation]

## 6. Remaining unknowns and search boundary

These are source gaps, not silently selected policies:

- **Current API Coding/Agentic full component lists, weights, normalization and update relationship to II v5.** S1/S2 state derived subsets; S3 retains TB2.1 in Coding while replacing it in II; dated articles prove older formulas only. S7/S8, current S3, S9, S10 and the current capability methodology were read. No current exact formula was found.
- **Coding/Agentic same-index cost per task and any sanctioned reuse of Intelligence cost.** The complete published OpenAPI was searched for Coding/Agentic cost names and cost references; both Free and paid model shapes were read. Current definitions and public charts publish II task cost, and the distinct agent benchmark publishes its own cost. Targeted official-site searches for `coding_index_cost`, `agentic_index_cost`, “Cost per Coding Index”, “Cost per Agentic”, and each area-index name with “cost per task” produced no matching area-model denominator.
- **Free performance's precise prompt preset and endpoint pooling.** The Free route parameters/envelope and shared performance schemas do not settle them. The legacy `/api-reference` page still documents `/api/v2/data/llms/models`, a 1k default, 1,000 requests/day, top-level medians and `median_time_to_first_answer_token` without `_seconds`. The current tiered route instead documents nested fields, 100 requests per fixed 24-hour window and the distinct schema above. These are different documented surfaces; do not import legacy defaults into the project's route. [S1, S2, S12]
- **Per-row reasoning-estimate provenance and complete operational cost/time.** Free exposes no measured/fallback reasoning flag, task tool/sandbox time, production network location, agent harness, supervision cost or workload-specific completion guarantee. Benchmark-cost/timing labels must not imply those measurements. [S1, S4, S5, S9]
